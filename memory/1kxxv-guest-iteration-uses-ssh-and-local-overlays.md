title: Guest iteration uses SSH and local overlays

When the agent runs inside the target Linux system, use its local command tool directly. SSH and the development bridge are only needed for access from another machine. Identify the OS, architecture, live versus installed state, and checkout before acting. Do not assume ignored Mac handoff notes or endpoints exist. See [Linux development](../docs/linux-development.md) for native dev shells, previews, and temporary installed-source overrides.

For remote access, use SSH for commands and transfers. Never type or paste commands into terminal windows through computer use: earlier synthetic input dropped key releases and left keys repeating. Slower typing is not a workaround.

Read ignored .local/SESSION.md for local connection details, then verify guest identity. Pass the current SSH port and verified host-key file explicitly; tooling defaults may target the retired builder. Raw QMP-added forwarding disappears when the host engine exits. The guest-dev bridge command also saves development.json in the selected .local VM state, and the updated factory launcher reads it on later starts. Development SSH stays in a local guest overlay, not shipped images.

For routine edits, build a host configuration that preserves the installed owner, storage, state versions, and development overlay. Never activate factory or live profiles on an installed guest. Prefer boot activation for login-manager changes, then a planned restart. Build, boot selection, and running generation are distinct.

Source snapshots avoid sharing the host home. Full image builds test provisioning and releases, not every desktop edit.

Sources: [workflow](../docs/ohmansy-development.md), [guest tooling](../tools/dev/guest-dev.py), [Nix instructions](../nix/AGENTS.md).

The reusable access rules live in nix/modules/development.nix, exported as ohmansy.nixosModules.development. Import alone is inert; ohmansy.development.enable needs an existing owner and explicit Ed25519 keys. Passwordless sudo defaults on for this opt-in mode and can be disabled separately. The shipped ohmansy-dev command manages a marked import and local overlay, builds before activation, shares the updater lock, and restores configuration/profile/runtime on activation failure. It refuses manual or edited overlays. Both it and the host generator import the selected release's module through specialArgs. Do not write unrooted absolute store paths into the local overlay: a future release plus GC could invalidate them. Guest SSH configuration and the Mac loopback port forward are separate; both start disabled.

On 2026-11-03 ARM flake checks passed for disabled behavior, required owner/key, SSH settings, optional sudo, and enabling the real module in every image profile (all rejected by image policy). The packaged CLI and an installed configuration generated by the command built; disabling restored the original configuration and evaluated SSH off. Python failure-injection tests covered activation rollback and concurrent edits. Live QMP add/remove passed on the preserved builder.

The user then updated the installed guest and enabled access with the shipped command. Its host key matched the fingerprint supplied by the user; strict SSH and passwordless sudo passed. After updating the signed Mac bundle, a clean guest shutdown and full app restart verified that the launcher restored the saved loopback forward without a QMP add command. A new guest boot ID, SSH, sudo, and active sshd/greetd confirmed the end-to-end path. Older installed OS/app versions still need an update before these commands and persistent forwarding are available. Live disabling and activation-failure recovery remain covered by configuration and failure-injection tests, not a live reboot test.
